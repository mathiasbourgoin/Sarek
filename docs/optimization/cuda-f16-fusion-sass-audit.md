# CUDA f16 fusion audit — SASS-level, no NVIDIA device

**Issue:** #107. **Follows:** #290 (`feat/f16-dsl-slice1`, head `434b13ff`).
**Date:** 2026-07-25. **Host:** no NVIDIA GPU. **Toolchain:** CUDA 13.3,
`ptxas`/`nvdisasm`/`nvcc` V13.3.73, `libnvrtc.so.13.3.33`.

> **Superseded in one respect (#110).** The recommendation at the end of this
> document — "removing it or keeping it is out of scope" — has since been
> acted on: the inert `"+f"` barrier was **removed** from the non-HIP branch of
> `sarek_f32_barrier`, after re-measuring byte-identical cubins on sm_75 through
> sm_121 for the codegen's current output. Everything else here still stands.
> The cross-backend rule, and what the other backends do about contraction, is
> [`docs/fp-contraction-policy.md`](../fp-contraction-policy.md).

## The question

#290 found that on HIP/gfx1100 the generated C was correct and the machine code
was not. An AMDGPU ISel combine emitted

```
v_fma_mixlo_f16 v0, v0, s2, 0        ; the f32 multiply AND the narrowing, fused
v_add_f16_e32   v0.l, 0x63d0, v0.l   ; an f32 add DEMOTED to binary16
```

Both skip a rounding the DSL mandates: Sarek's f16 surface promises arithmetic
in f32 with narrowing as a separate round-to-nearest-even step. 620 of 63488
finite binary16 inputs disagreed with the interpreter. `-ffp-contract=off/on/fast`
and `#pragma clang fp contract(off)` left the ISA byte-identical — the combine
sits below the C-level FP controls. The fix was an opacity barrier,
`asm volatile("" : "+v"(x))`, on the narrowing's argument. A PTX `"+f"` variant
was added for CUDA at the same time, and it compiles, but nobody had checked
whether CUDA ever had the defect or whether the barrier does anything there.

That check does not need a GPU. `ptxas` turns PTX into a cubin and `nvdisasm`
prints SASS, which is the actual machine code — the same evidence class that
caught the AMD bug, not a proxy for it.

## Verdict

**CUDA never had the defect, on any architecture checked, and the barrier is
inert there.** The `"+f"` barrier compiles down to an *empty* inline-asm block
that NVVM erases entirely; the PTX instruction stream is identical with and
without it, and the resulting cubins are byte-identical on all seven targets.
The non-fusion comes from `ptxas`, not from the barrier.

Claim tier: this shows **the fusion is absent from the SASS that ptxas 13.3
emits for these targets**. It is *not* "verified on CUDA" — see
[Residual risk](#residual-risk).

## Per-architecture result

Source: the `midround` kernel from `sarek-hip/test/test_hip_f16.ml`, i.e.
`out.(i) <- f16_of_f32 (f32_of_f16 (f16_of_f32 (f32_of_f16 inp.(i) *. 1.1)) +. 1000.0)`,
generated by `Sarek_ir_cuda`, compiled through nvrtc to PTX and assembled by
`ptxas` for each target.

| arch | fused without barrier? | fused with barrier? | deciding instructions |
|---|---|---|---|
| sm_75 | **no** | **no** | `FMUL` + `F2F.F16.F32` (separate); `FADD` |
| sm_80 | **no** | **no** | `FMUL` + `F2FP.PACK_AB`; `FADD` |
| sm_86 | **no** | **no** | `FMUL` + `F2FP.PACK_AB`; `FADD` |
| sm_89 | **no** | **no** | `FMUL` + `F2FP.F16.F32.PACK_AB`; `FADD` |
| sm_90 | **no** | **no** | `FMUL` + `F2FP.F16.F32.PACK_AB`; `FADD` |
| sm_100 | **no** | **no** | `FMUL` + `F2FP.F16.F32.PACK_AB`; `FADD` |
| sm_120 | **no** | **no** | `FMUL` + `F2FP.F16.F32.PACK_AB`; `FADD` |

On every target the cubin is **byte-identical** between the barriered and
unbarriered sources (`cmp` on the cubin, and `diff` on the disassembly).

The f32 **add** is not demoted either — this was the second and broader half of
the AMDGPU defect, and it does not track the multiply case, so it was checked
separately. `FADD R0, R0, 1000` is a binary32 add on all seven; no `HADD2`
without an f32 marker appears anywhere.

### Representative SASS (sm_90, without the barrier)

```
HADD2.F32             R0, -RZ, R2.H0_H0   ; f16 -> f32 widening (exact)
FMUL                  R0, R0, 1.10000002  ; the f32 multiply, intact
F2FP.F16.F32.PACK_AB  R0, RZ, R0          ; separate f32 -> f16 narrowing
HADD2.F32             R0, -RZ, R0.H0_H0   ; f16 -> f32 widening
FADD                  R0, R0, 1000        ; the f32 add, NOT demoted
F2FP.F16.F32.PACK_AB  R0, RZ, R0          ; separate f32 -> f16 narrowing
```

This mirrors the clean HIP sequence (`v_cvt_f32_f16` / `v_mul_f32` /
`v_cvt_f16_f32`) one-for-one.

`HADD2.F32 Rd, -RZ, Rs.H0_H0` is ptxas's idiom for `cvt.f32.f16`: a half-typed
add of negative zero with an f32 result. It is a widening, which is exact, so it
introduces no rounding. On sm_80 an `HFMA2.MMA R5, -RZ, RZ, 0, <imm>` also
appears at offset `0x0020`; that is the immediate-materialisation idiom (it puts
the integer stride `2` in R5 for the following `IMAD.WIDE`) and is nowhere near
the floating-point data path.

## Why the barrier does nothing

`asm volatile("" : "+f"(x))` has an *empty* assembly template. NVVM emits it as
an empty inline-asm block and coalesces the register, so the only difference
between the two PTX modules is a virtual-register-count declaration:

```
$ diff <(norm midround_nobarrier.ptx) <(norm midround_barrier.ptx)
12c12
< .reg .f32 	%f<5>;
---
> .reg .f32 	%f<9>;
```

Confirmed identical on the real path too: nvrtc 13.3 and nvcc 13.3 produce the
same PTX for the unbarriered source, and the barriered/unbarriered SASS is
identical under nvrtc as well.

By contrast the AMDGPU `"+v"` barrier is load-bearing precisely because the
LLVM AMDGPU backend *is* the thing that fuses, and the constraint pins the value
in a VGPR ahead of it.

## Where the non-fusion actually comes from

Not from `cuda_fp16.h`'s inline asm, and not from the barrier. Hand-written PTX
with plain `mul.f32` / `cvt.rn.f16.f32` and no inline-asm wrapping at all, run
through `ptxas -O3`, gives the same unfused sequence:

```
HADD2.F32             R0, -RZ, R2.H0_H0
FMUL                  R0, R0, 1.10000002
F2FP.F16.F32.PACK_AB  R0, RZ, R0
HADD2.F32             R0, -RZ, R0.H0_H0
FADD                  R0, R0, 1000
F2FP.F16.F32.PACK_AB  R0, RZ, R0
```

So `ptxas` treats `cvt.rn.f16.f32` as a rounding step it may not absorb. A
`static_cast<__half>(...)` narrowing instead of `__float2half` gives the same
result, so the conclusion does not rest on which conversion spelling the
generator picks.

## Flags do not change it (checked, not assumed)

The lesson of #290 is that the obvious flag did nothing, so every flag below was
measured rather than reasoned about. Assembled for sm_90, both source variants:

| nvcc flags | arithmetic stream |
|---|---|
| *(default)* | `FMUL` / `F2FP` / `FADD` / `F2FP` |
| `-fmad=false` | identical |
| `-fmad=true` | identical |
| `--prec-div=true --prec-sqrt=true -fmad=false` | identical |
| `--extra-device-vectorization` | identical |
| `-use_fast_math` | still unfused, but `FMUL.FTZ` / `FADD.FTZ` |
| `-ftz=true` | still unfused, but `FMUL.FTZ` / `FADD.FTZ` |

`ptxas -O0/-O1/-O2/-O3` and `--allow-expensive-optimizations=true`: unfused at
every level. `-O0` emits `F2F.F16.F32` where `-O1` and up emit the packed
`F2FP` form; both are single-instruction conversions.

**Hazard worth recording, separate from fusion:** `-use_fast_math` and
`-ftz=true` add `.FTZ` to the f32 arithmetic. That flushes binary32 subnormals
and *would* diverge from the interpreter — `1e-5` is already lane 5 of the
`test_hip_f16` input array. SPOC does not pass either flag: `Cuda_nvrtc.compile_to_ptx`
supplies only `--gpu-architecture=` and `--include-path=`. This is a reason not
to add them, not a live defect.

## What is now machine-checked

`sarek-cuda/test/test_cuda_f16_sass.ml`. It runs the whole chain host-side —
generated CUDA → nvrtc → PTX → ptxas → cubin → nvdisasm → SASS — for the seven
architectures above, and fails if the f32 discipline is broken:

- no binary16 arithmetic on the data path (`HMUL*`/`HFMA*`/`HADD*`/`HSET*`/`HMNMX*`,
  excluding the immediate-materialisation and widening idioms);
- exactly one `FMUL` and exactly one `FADD` — a fused form would absorb them;
- exactly two f32→f16 narrowings and two f16→f32 widenings — a fused form folds
  one away, which a mere "contains a narrowing" assertion would not notice.

It skips cleanly without nvrtc, without CUDA headers, or without `ptxas`/`nvdisasm`
on PATH, and skips individual architectures the local `ptxas` does not know, so
an older toolkit still checks the targets it supports.

Two things keep it from being vacuous:

1. A **positive control** in the test itself: a CUDA source using `__hmul`/`__hadd`
   (native binary16 arithmetic, which the DSL cannot express) must be classified
   as fused. It is — `HFMA2 R0, R2.H0_H0, R0.H0_H0, 1000, 1000`, the CUDA
   analogue of `v_fma_mixlo_f16`. If the classifier ever stops seeing it, the
   test fails rather than silently passing.
2. **Red on mutation**, checked by hand: pointing the gate at that fused source
   makes it fail with the fused instruction quoted.

The pre-existing `test_cuda_f16_nvrtc` gate is not a substitute — it asserts on
PTX, and the AMDGPU fusion happened strictly below the equivalent level.

## Residual risk

What has **not** been shown:

- **No execution.** No f16 CUDA kernel has been run on NVIDIA hardware. The
  interpreter-agreement claim remains HIP-only. What remains unverified is
  narrow, though: the codegen question is settled at the machine-code level, so
  the gap is a hardware-level conversion-rounding difference (does `F2FP.F16.F32`
  actually round to nearest-even on ties?), not a codegen one. `F2FP`/`F2F` with
  `.F16.F32` is an architecturally specified round-to-nearest-even conversion,
  and the equivalent step was measured correct in isolation on AMD.
- **Offline ptxas, not the driver JIT.** SPOC loads PTX via `cuModuleLoadData`,
  so on a real machine the assembling compiler is the *driver's* ptxas, a
  different build from `/opt/cuda/bin/ptxas`. Nothing here constrains it. The
  test is written so that running it on a machine with a matching toolkit
  narrows this; only execution closes it.
- **CUDA 13.3, not the CI's 12.6.** Everything above is one toolkit version.
  Nothing older is installed on this host, so no 12.6 comparison was possible.
  The result is stable across seven architectures and every optimisation level
  and flag combination tried, which argues it is a durable ptxas property rather
  than a 13.3 accident — but that is an argument, not a measurement. If the gate
  ever fails on CI at 12.6 while passing here, that difference is the finding
  and should not be papered over.
- **One kernel shape.** `midround` is the shape that exposed both halves of the
  AMDGPU defect, plus `scale` as a cross-check. A different expression shape
  could in principle reach a different ptxas path.

## Recommendation

The `"+f"` barrier on the CUDA path costs nothing measurable — the cubins are
byte-identical, so it is zero instructions and zero registers — but it also buys
nothing, and it reads as protection that is not there. Removing it or keeping it
is a codegen change and is out of scope for #107; the SASS gate makes the
guarantee checkable either way, and would catch it if a future toolchain started
fusing.

## Reproducing

```sh
export PATH=/opt/cuda/bin:$PATH
dune build ./sarek-cuda/test/test_cuda_f16_sass.exe
./_build/default/sarek-cuda/test/test_cuda_f16_sass.exe --verbose
```

Expected: `f16 SASS gate: f32 discipline intact on 7/7 architectures` and
`positive control on sm_75: fusion detected (HFMA2)`.
