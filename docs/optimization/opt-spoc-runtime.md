# SPOC/Sarek Runtime-Side Optimization Evaluation

Scope: runtime and codegen changes that improve throughput/latency without
changing the surface DSL. Grounded in the actual code as of this branch
(`reconcile/queue-2026-07-01`). No code was modified; this is an evaluation
doc only.

Companion docs in this directory (`L8-aligned-host-abi.md`,
`L9-byvalue-aggregate-params.md`, `L10-inherent-limits.md`) cover ABI/param
limits; this doc is scoped to *runtime performance*, not ABI legality.

---

## 1. SoA↔AoS for custom vectors (headline item)

### 1.1 Current state — AoS, packed, no padding

A `custom_type` vector (e.g. a `point3d = {x:float32; y:float32; z:float32}`
vector) is laid out **packed AoS** on both host and device, and the two sides
are required to agree byte-for-byte:

- **Host layout** — generated by the PPX in
  `sarek/ppx/Sarek_ppx.ml:614-702` (`generate_custom_value`). `calc_offsets`
  (line 616) assigns each field a cumulative byte offset with **no padding**;
  `get`/`set` close over `base_off = idx * size_expr` (lines 665-701) and do
  raw `Ctypes` pointer arithmetic per field (`Custom_helpers.read_*`/`write_*`
  in `sarek/core/Vector_types.ml:29-89`). For `point3d`, `size_expr = 12`,
  fields at offsets 0/4/8.
- **Device layout** — `spoc/ir/Sarek_ir_layout.ml` mirrors the exact same rule
  by contract (see the module doc comment at the top: "Records: packed
  cumulative offsets, NO padding ... mirrors the host PPX layout exactly").
  `record_layout` (line 188) folds fields left-to-right with
  `flatten_field ~offset` accumulating sizes, no alignment padding inserted
  — only a *rejection* of a layout that would misalign a leaf
  (`Misaligned_field`, `Sarek_ir_layout.ml:36-47`).
- **Device buffer** — one `cuMemAlloc` of `length * elem_size` bytes
  (`sarek-cuda/Cuda_api.ml:303-308`, `Memory.alloc_custom`); one base pointer
  is bound as a single kernel parameter (`Sarek_ir_ptx_kernel.ml:69-93`: one
  `.param .u64` + one `.param .u32` length, **not** one pointer per field).
- **Device addressing (`spoc/codegen/Sarek_ir_ptx_mem.ml`)** —
  `emit_agg_elem_addr` (lines 191-205) computes the *element* base address as
  `r_base + idx * stride` where `stride = elt_stride t` = the full packed
  struct size (12 for `point3d`, from `Sarek_ir_layout.elttype_layout`).
  `emit_field_load`/`emit_field_store` (lines 213-241) then do one
  `ld.global.f32 [%rd+off]` / `st.global.f32 [%rd+off]` per field at a fixed
  byte offset (0, 4, 8) from that element base.

**The coalescing problem**: for a warp of 32 threads reading `points[tid].x`,
consecutive threads' target addresses are `base + tid*12`, i.e. a **12-byte
stride**, not the natural 4-byte stride of `float32`. Per the standard
GPU memory-coalescing rule (NVIDIA CUDA C Programming Guide, "Device Memory
Accesses" — a warp's accesses coalesce into the minimum number of 32/64/128-B
transactions when addresses are contiguous within a cache-line-sized
window), a 12B-strided `float32` read forces the memory controller to fetch
3× the cache-line traffic actually consumed. For a 3-field record this is
the textbook **1/3 bus-utilization case** (each 128B/32B sector serves only
~1 useful 4-byte lane per field per pass, and the load has to be issued as 3
separate transactions instead of 1 coalesced one). This is a **memory
bandwidth-bound** loss, not a correctness one — it shows up directly as wall
time on any kernel that's bandwidth-bound and touches only 1-2 fields of a
wider record (a very common pattern: n-body reads `.mass` broadcast + writes
`.vx/.vy/.vz`, a stencil reads only `.temperature`, etc.)

### 1.2 Proposed: SoA storage for custom vectors, same user-facing API

**(a) Storage.** Replace the single `Custom_storage {ptr; custom; length}`
buffer with a `Custom_storage_soa` variant holding **one sub-buffer per
scalar leaf** (from `Sarek_ir_layout.leaf` — this is already computed today
in `spoc/ir/Sarek_ir_layout.ml:96-102`/`record_layout`, it's just discarded
after alignment-checking; SoA reuses the *same* leaf list as the storage
plan instead of only a validation artifact). For `point3d` that's 3 buffers
of `length * 4` bytes each, instead of 1 buffer of `length * 12` bytes.
Nested records flatten to their leaves exactly as `Sarek_ir_layout` already
does (dotted `leaf_path`, e.g. `pos.x`) — no new flattening logic needed,
just a new *consumer* of the existing flattening.

**(b) Where the transform lives — genuinely simpler than AoS.**
- *Host get/set* (PPX-generated, `Sarek_ppx.ml:663-702`): instead of
  `base_off = idx*12; read at base_off+{0,4,8}`, each field's accessor
  becomes `read_at(field_base_ptr, idx*4)` — the multiply is by the *leaf's
  own size* (uniformly 4 or 8), and there is **no per-record stride**
  because each leaf lives in its own buffer. This removes the
  struct-offset addition entirely; it's a strict simplification.
- *Device emitter* (`Sarek_ir_ptx_mem.ml`): `emit_agg_elem_addr` currently
  does `mul.wide.u32 stride=12; add.u64 r_base` **once**, then reads at
  fixed sub-offsets from that one address. Under SoA, drop
  `emit_agg_elem_addr`+`emit_field_load`/`emit_field_store`'s offset
  parameter entirely and instead do, per leaf, exactly what a plain scalar
  vector already does today (`mul.wide.u32 idx, leaf_size; add.u64
  r_base_leaf` — this is the *scalar* array addressing path that already
  exists elsewhere in the same file for `TInt32`/`TFloat32` arrays, lines
  60-77). **A record-of-N-scalars under SoA is emitted as N independent
  scalar-array accesses with a shared index** — this is less code than the
  current aggregate path, not more; the current `agg_field_path` byte-offset
  folding (lines 159-185) disappears completely for the SoA case.
- *Kernel signature* (`Sarek_ir_ptx_kernel.ml:69-93`): a custom-vector
  parameter currently lowers to `(ptr, len)`. Under SoA it lowers to `(ptr_0,
  ptr_1, ..., ptr_{n-1}, len)` — N base pointers sharing one length. This is
  the one place the change is *not* simpler: kernel arity grows with field
  count, so `Kernel_args`/`RSA_Buffer`/`bind_to_kargs`
  (`sarek/core/Transfer.ml:37-89`, `Framework_sig.exec_arg`) all need to bind
  N buffers per vector argument instead of 1. This is mechanical but touches
  the ABI surface documented in `L9-byvalue-aggregate-params.md` — budget
  real effort here, not just codegen.

**(c) Transparent-choice design.** Two viable knobs, not mutually exclusive:
  - *Per-vector layout tag at creation*: `Vector.create ~layout:AoS|SoA kind
    n` — decided once, matches the `custom_type` record already carrying
    `elem_size`/`get`/`set`; the PPX would emit **both** an AoS and an SoA
    `custom_type` value per record type (cheap — it's generated code) and
    `Vector.create` picks one. Existing AoS code (host `get`/`set`, external
    `.cu`/`.ptx` files written against the packed layout) keeps working
    unchanged when `AoS` is chosen; this is the **compatible default**.
  - *Per-kernel-launch transform*: leave storage as AoS at rest (host-facing,
    interop with `of_ctypes_ptr`/`sub_vector`, both of which alias raw
    memory and would break under SoA) and transpose to a *scratch* SoA
    buffer only for the duration of a kernel launch, transposing back after.
    This trades an extra device-side transpose (itself a coalesced,
    bandwidth-bound kernel) for zero host-API disruption — worth it only
    when the transposed layout is reused across **many** launches (e.g. an
    iterative solver) so the one-time transpose cost is amortized; for a
    single launch it's a wash or a loss (see 1.4).
  Recommendation: ship (a) per-vector tag first — it's the one that actually
  removes the memory traffic rather than moving it around, and it fits
  the existing `custom_type` abstraction with no new indirection layer.

**(d) Coalescing gain estimate.** For a kernel that reads/writes one field of
an N-field record: AoS forces `N`× the minimum transaction count (bus
efficiency ≈ `1/N`, capped by the sector/cache-line granularity — 3-field
`float32` records land close to the textbook 1/3 case cited in NVIDIA's
coalescing model). SoA restores full coalescing for that access — a
same-order-of-magnitude (2-3×) improvement is a defensible bandwidth-bound
estimate for kernels dominated by single/few-field access over wide
records, and no change for kernels that already read/write **whole
records** every thread (see (e) — AoS is *at worst* equal there, and
sometimes better due to spatial locality within one cache line, per the
classic AoS-vs-SoA tradeoff literature).

**(e) Interaction with whole-record copies and host get/set.** Two subtleties
that make this non-trivial:
  - *Whole-record device access* (`emit_agg_elem_load`,
    `Sarek_ir_ptx_mem.ml:283-305`, SROA binding: one `ld.global` per leaf
    already, in *declaration order*) already touches each field with a
    separate load even under AoS — so whole-record access is **already
    N loads today**, just from one cache line under AoS vs. N cache lines
    under SoA. This means whole-record-copy kernels (e.g. a vector `blit`,
    or a kernel that reads `p` and writes `p'` unchanged) are the one
    workload class where **SoA can be worse** than AoS (N cache lines
    touched instead of 1) — this must be called out, not glossed over, in
    any per-vector layout decision. It argues for the per-vector tag (c)
    being explicit and workload-driven, not a blanket default flip.
  - *Host `get`/`set`* (`sarek/core/Vector.ml:74-108`) call the
    `custom_type`'s `get`/`set` closures directly — these are exactly the
    PPX-generated accessors from 1.2(b), so host-side semantics (bounds
    checks, `Stale_GPU` marking on `set`) are untouched; only the closures'
    internals change. `Vector.of_ctypes_ptr` (`Vector.ml:27-28`) and
    `sub_vector` (`Vector.ml:250-252`) both assume **one contiguous host
    buffer** they can alias/offset into — these are AoS-only operations by
    construction and must either stay AoS-restricted or grow an SoA variant
    that offsets all N sub-buffers in lockstep. Treat as AoS-only for v1.

**(f) AoSoA middle ground.** Tile records into blocks of `W` (e.g. `W=32` =
warp width): store `W` records' worth of each field contiguously, then the
next tile. This gets full coalescing *within a tile* while keeping
whole-tile spatial locality closer to AoS's per-record locality, and is the
standard mitigation in HPC codes (e.g. AoSoA in Cabana/ExaMPM, SPH codes)
for exactly the "sometimes read one field, sometimes the whole record"
access mix. It is strictly more implementation work than either pure SoA or
pure AoS (tile-boundary arithmetic on both host PPX and PTX emitter) — treat
as a **follow-on**, not a v1 target, unless profiling on a real kernel shows
pure SoA regresses whole-record workloads enough to matter.

**(g) Migration/compat.** External `.cu`/`.ptx` files loaded via
`Execute.run_source`/`run_source_file` (`sarek/execute/Execute.ml:661-775`)
are written against the AoS byte layout by hand — an SoA vector fed to one
of these would silently corrupt data (wrong pointer arithmetic on the
handwritten side, no type checking crosses that boundary). SoA must be
**opt-in per vector**, defaulting to AoS, and ideally rejected (or loudly
flagged) as an argument to `run_source`/`run_source_file` unless the caller
explicitly acknowledges the layout. `sarek/tests/codegen_golden/*` golden
tests would also need an SoA variant added rather than replacing the AoS
goldens.

**Cost: M (moderate-large).** Addressing math is a genuine *simplification*
in the emitter (1.2b) and the host PPX. The cost is concentrated entirely in
plumbing N buffers through `Vector_types`'s `device_buffers` table,
`Transfer.ml`'s alloc/transfer/free paths, `Kernel_args`/`RSA_Buffer`
binding, and the kernel-parameter arity change in
`Sarek_ir_ptx_kernel.ml` — all mechanical, well-specified by the existing
`Sarek_ir_layout.leaf` list, but touching several files each requiring care
around the `L9-byvalue-aggregate-params.md` ABI constraints.

**Verdict: pursue, opt-in per-vector, v1 = flat records only (reject nested
records / variants — variants don't have a well-defined SoA split by tag).**
Gate the decision on profiling one real kernel (n-body or a stencil already
in `sarek/tests/e2e/`) old-vs-new before committing to default-on anywhere.

## 2. Pinned (page-locked) host memory

**Current state**: no pinned memory anywhere in the CUDA backend. `grep` for
`cuMemHostAlloc`/`cuMemHostRegister`/`cuMemAllocHost` in
`sarek-cuda/Cuda_api.ml` returns nothing. All host-side vector storage is
plain OCaml `Bigarray`/`Ctypes` heap memory (`Vector_types.ml`,
`Vector_transfer.ml:15-27`), and every transfer goes through
`Cuda_api.ml:316-342` (`Memory.host_to_device`/`device_to_host`/
`host_ptr_to_device`/`device_to_host_ptr`), all of which call the
**pageable** `cuMemcpyHtoD`/`cuMemcpyDtoH` variants against whatever pointer
`Ctypes.bigarray_start` returns.

**Gain**: pageable-memory transfers are staged through an internal
pinned bounce buffer by the driver; pinned host memory skips that staging
copy. NVIDIA's own guidance (Best Practices Guide, "Pinned Memory") puts
this at roughly a 2× bandwidth improvement on PCIe-class links, and it's a
prerequisite for true async (`cuMemcpyAsync`) transfers (item 3) — pageable
memory silently falls back to synchronous behavior even when an async API
is used.

**API impact**: allocating pinned memory means the `Bigarray`/`Ctypes`
buffer itself must come from `cuMemAllocHost`/`cuMemHostAlloc`, not the OCaml
GC heap — this is a bigger change than it sounds because `Vector.create`
today allocates a normal `Bigarray.Array1` (GC-managed, movable-by-major-GC
only in the sense that Bigarray external data doesn't move, but the *point*
is CUDA has no way to know an arbitrary Bigarray's pages happen to be
pinned). Two workable shapes: (i) an opt-in `Vector.create ~pinned:true`
that allocates via a small `cuMemHostAlloc` C stub and wraps the result as a
`Bigarray` over foreign memory (`Bigarray.Array1.of_genarray` /ctypes bigarray
view — plumbing already exists for `Custom_storage` raw pointers, see
`of_ctypes_ptr`, `Vector.ml:27-28`, so the wrapping mechanism is not new);
or (ii) `cuMemHostRegister` on an *existing* Bigarray's pages post-hoc
(no allocation-path change, but register/unregister has real per-call
overhead and page-alignment requirements the current `Bigarray.Array1.create`
doesn't guarantee). (i) is cleaner given the codebase's existing
foreign-pointer wrapping path.

**Cost: S-M.** Isolated to `Cuda_api.Memory` + a new `Vector.create` option;
doesn't touch codegen or the IR at all.

**Priority: high** — it's the cheapest lever here and a hard prerequisite
for item 3.

## 3. Async transfers + stream overlap

**Current state**: every transfer path in `Cuda_api.ml:316-342` is the
**blocking** `cuMemcpyHtoD`/`cuMemcpyDtoH` (not `*Async`), always on the
default/null stream implicitly (no stream argument threaded through
`Memory.host_to_device` etc. at all). The comment at
`Cuda_api.ml:314-315` even says explicitly: *"A blocking memcpy on the
default stream drains all prior launches on that stream, so it is a safe
point to release the device's retained kernargs"* — i.e. the kernarg-retention
design (item below) currently **relies on** transfers being blocking. `Transfer.ml`'s
`to_device`/`to_cpu` (lines 262-373) never pass a stream to the backend at
all — the `Framework_sig.BACKEND.Memory` interface for CUDA has no
stream-taking transfer entry point.

Kernel *launches*, by contrast, already support a stream argument end to end
— `Kernel.launch ~stream` (`Cuda_api.ml:621, 659-663`) and the full
`Stream` module (`create`/`destroy`/`synchronize`/`default`,
`Cuda_api.ml:358-379`) exist and are exposed at `Transfer.ml:428-474`
(`create_stream`/`default_stream`/`synchronize_stream`/`destroy_stream`).
So the **launch side of async execution already works**; only the **memory
side** is missing.

**The foundation that makes this tractable — kernarg-lifetime retention
(PR #221, `Cuda_api.ml:54-95, 682-692`)**: `cuLaunchKernel` is async, and the
driver only snapshots parameters synchronously — the *pointed-to* host
buffers must outlive the launch until the stream drains. The code already
solves exactly this problem for kernel *arguments* (`pending_kernargs`,
keyed by `(device_id, stream_key)`, retired on `Stream.synchronize`/
`Device.synchronize`). Making transfers async needs the **same
liveness discipline** applied to the *source* buffer of an
`cuMemcpyHtoDAsync`/`cuMemcpyDtoHAsync` (the OCaml-side Bigarray must not be
freed/reused by the GC, and per item 2, ideally must be pinned) — this is
conceptually the same retain/retire pattern already implemented, not new
design.

**Proposal**: (i) land item 2 (pinned memory) first — async transfers on
pageable memory silently degrade to synchronous; (ii) add
`Memory.host_to_device_async ~stream`/`device_to_host_async ~stream` using
`cuMemcpyHtoDAsync`/`cuMemcpyDtoHAsync`, retaining the source/dest buffer via
the existing `retain_kernargs`/`retire_stream` machinery (rename generically,
it's really "retain until stream X drains", not kernarg-specific); (iii)
thread an optional `stream` parameter through `Transfer.to_device`/`to_cpu`
and `Execute.run_vectors` so a caller can pipeline transfer(stream A) with
compute(stream B) — classic double-buffered compute/copy overlap.

**Gain**: for a bandwidth-and-compute-mixed workload with roughly equal
transfer and compute time, overlap can approach a 2× end-to-end speedup
(Amdahl-style: hiding the smaller of the two behind the larger); for
transfer-dominated or compute-dominated workloads the gain shrinks toward
zero. This is workload-dependent and should be estimated per-benchmark, not
promised as a flat number.

**Cost: M.** Stream plumbing already exists; the new work is the async
Memory entry points + generalizing the kernarg-retention module to a
generic "retain until stream drains" utility + threading an optional stream
through `Execute.run_vectors`'s currently-implicit synchronous pipeline.

**Priority: medium-high**, but sequenced *after* item 2.

## 4. Kernel fusion (`Sarek_fusion.ml`, 1318 lines)

**What it fuses today** (all IR-level, pre-codegen, in
`sarek/sarek/Sarek_fusion.ml`):
- **Elementwise producer→consumer fusion** (`can_fuse`/`fuse`, lines
  400-554): when kernel A writes `intermediate[idx]` and kernel B reads
  `intermediate[idx]` with the **same** index expression (`OneToOne`
  pattern, `expr_equal` check), B's read is substituted with A's computed
  expression and the intermediate array parameter is eliminated. Rejects
  fusion across a barrier (`no_barriers`) or an atomic in either kernel
  (`no_atomics`, line 434, with an explicit rationale comment: an atomic's
  ordering guarantee depends on the kernel boundary).
- **Map→Reduction fusion** (`can_fuse_reduction`/`fuse_reduction`, lines
  639-810): detects a reduction access pattern via
  `detect_reduction_pattern` (line 650) and fuses a map kernel directly into
  a reduce kernel, again eliminating the intermediate.
- **Map→Stencil fusion** (`can_fuse_stencil`/`fuse_stencil`, lines 812-1077):
  handles `arr[idx±k]` neighbor access (`Stencil` pattern,
  `analyze_pattern`/`extract_offset`, lines 284-333), computing a
  `stencil_radius` (line 823) and substituting shifted producer expressions
  (`subst_stencil_reads`/`shift_expr`, lines 923-976) — this is the
  general case (elementwise fusion is a stencil with radius 0).
- **Pipeline-level chaining** (`fuse_pipeline_list`/`fuse_pipeline`, lines
  590-637): iterates a `kernel list` pairwise, applying whichever of the
  three fusion rules applies at each step (`fuse_auto`, lines 806-812
  dispatches reduction → stencil → elementwise in that priority order).
- **Phase-5 auto-fusion heuristics** (lines 1079+): a should-we-fuse
  decision tree (`Rule 0`..`Rule 4`+) — e.g. "Rule 3: Map→Reduction is
  always good" (line 1145), "Rule 4: Stencil needs shared memory - maybe
  beneficial" (line 1148) — plus the atomics/barrier hard rejects from
  `can_fuse`.

**What's missing / not attempted**:
- **Multi-stage reduction fusion** (reduce→reduce, e.g. a tree of partial
  sums across multiple reduction kernels) — only map→single-reduce is
  handled; a reduce-of-reduce chain isn't a case in `can_fuse_reduction`.
- **Fusion across kernels with *different* thread-index shapes** (e.g. a
  transpose between two kernels, or a kernel whose thread grid differs from
  its neighbor's) — everything here requires the *same* index expression
  (`expr_equal prod_idx cons_idx`, line 422) or a fixed-offset stencil; a
  genuine reshape/gather in between blocks fusion entirely (falls to
  `Gather`/`Unknown` access pattern, which `analyze_pattern` explicitly
  never marks fusable).
- **Cross-vector-argument fusion beyond one `intermediate` name at a time**
  — `fuse_pipeline_list` fuses one named array per step; a kernel producing
  *multiple* intermediates consumed by different downstream kernels isn't
  automatically explored as a DAG (it's a linear pipeline list, not a
  general dependency graph).
- **Horizontal fusion** (two independent kernels over the same index space
  merged to amortize launch overhead / improve occupancy) is absent —
  everything here is *vertical* (producer→consumer) fusion.

**Gain class**: vertical fusion's main win is eliminating a global-memory
round trip for the intermediate array (one fewer full write + full read of
`N` elements) plus one fewer kernel-launch overhead — for launch-overhead-
bound pipelines (many small kernels) this can be the dominant cost; for
memory-bound pipelines it directly cuts total bytes moved by up to 2×
per eliminated intermediate. Reduction fusion additionally avoids
materializing the pre-reduction array at all. This is a **strict, already-
implemented win** wherever `can_fuse*` accepts — the main opportunity is
applying it more places (multi-stage reduction, DAG-shaped pipelines)
rather than fixing anything broken.

**Cost / priority**: extending to reduce-of-reduce and DAG-shaped pipelines
is **M**, self-contained to this one file and its 1318 lines already
establish the pattern to extend. **Priority: medium** — real but secondary
to items 1/2/3 which address problems with zero existing mitigation, versus
fusion which already does the common cases.

## 5. Transfer avoidance (dirty-tracking / lazy transfer)

**Current state: already substantially implemented**, more so than the task
prompt assumed — worth stating plainly since it changes the framing of this
item from "build it" to "audit it."

`Vector.location` (`sarek/core/Vector_types.ml` via `Spoc_core_base`, used
throughout `Vector.ml`) is a 5-state machine: `CPU | GPU of Device.t | Both
of Device.t | Stale_CPU of Device.t | Stale_GPU of Device.t`. `Vector.set`
(`Vector.ml:88-104`) marks `Both`/`GPU` → `Stale_GPU` on a host write (GPU
copy now stale); `mark_vectors_stale` in `Execute.ml:369-383` marks `Both` →
`Stale_CPU` after a kernel writes a vector on device (host copy now stale).
`Transfer.to_device` (`Transfer.ml:262-306`) explicitly **skips the
transfer** when the vector is already `GPU`/`Both`/`Stale_CPU` on the
*target* device (lines 278-283: `-> Log.debug "-> skip"`), and only pays the
`host_ptr_to_device` cost when the location says the device copy is
genuinely absent or stale. `Transfer.to_cpu` (lines 312-358) has the
symmetric skip for `Stale_GPU` (CPU is already authoritative, no-op) and
`CPU` (no device buffer at all).

So **`Execute.run_vectors`'s call to `transfer_vectors_to_device` before
every launch (`sarek/execute/Execute.ml:576-577`) is not a redundant
round-trip in the common case** — it's a cheap location check that
short-circuits to nothing when the device copy is already current. The
actual redundant-transfer risk is narrower than "every run re-transfers":
it's (i) **multi-device ping-pong** — `to_device` when the vector is
`GPU d'`/`Stale_CPU d'` for a *different* device `d'` unconditionally routes
through the host (`copy_device_to_host vec d'`, `Transfer.ml:273-275`) before
transferring to the new device — there is no device-to-device peer copy path
(`Memory.device_to_device`/`cuMemcpyDtoD` exists in `Cuda_api.ml:344-348` but
`Transfer.to_device` never calls it), so a vector alternating between two
GPUs always bounces through the host even when a direct P2P copy would be
cheaper; and (ii) **forced re-sync** — `to_cpu ~force:true` (used after
kernel writes when a caller needs the CPU copy despite `Both` claiming
sync) always re-transfers even if the caller doesn't actually need fresh
data yet (this is a correctness-safe default, not a bug, but it's a spot
where an explicit-sync API would let a caller defer the cost).

**Proposal**: (a) add a `Memory.device_to_device`-backed peer-copy path in
`Transfer.to_device` for the same-framework multi-device case, avoiding the
host bounce; (b) leave the location-based skip logic as-is — it already does
the job item 5 was asking about.

**Cost: S.** (a) is a small, local change to one function in `Transfer.ml`.

**Priority: low-medium** — only matters for genuinely multi-GPU workloads,
which the test suite (`sarek/tests/`) doesn't appear to exercise heavily.

## 6. Allocation caching / memory pool

**Current state**: `Transfer.ensure_buffer` (`Transfer.ml:187-238`) allocates
a device buffer for a vector **once**, lazily, and caches it in
`vec.device_buffers : (int, device_buffer) Hashtbl.t` keyed by device id —
so *for one long-lived vector*, `cuMemAlloc` is paid once, not once per
kernel launch; this part is already efficient. `Gpu_memory.ml` adds a GC
finalizer (line 163-178) that frees device buffers when a vector is
collected, plus a `with_retry` wrapper (lines 130-143) that does
`Gc.full_major`/`Gc.compact` and retries on `cuMemAlloc` failure — this is
allocation-failure resilience, not a pool.

**What's missing**: there is **no pool across distinct vectors**. A common
pattern in iterative workloads — creating a fresh temporary vector each
iteration (e.g. `Vector.create` inside a loop for a scratch buffer, or the
`Sarek_fusion`-eliminated-but-not-always-eliminated intermediate arrays) —
pays a fresh `cuMemAlloc`/`cuMemFree` (or waits for GC-triggered
`register_finalizer`/`track_gc_free`) every time, even when the size is
identical to a just-freed buffer. `cuMemAlloc`/`cuMemFree` are not free —
they synchronize the context in the CUDA driver in the general case, and
under GC-deferred freeing (finalizers only run at a major GC), a hot loop
that allocates a scratch vector per iteration can accumulate real GPU memory
pressure before the GC catches up, which is exactly the scenario
`with_retry`'s GC-retry exists to paper over rather than avoid.

**Proposal**: a size-bucketed free-list keyed by `(device_id, elem_size,
rounded-up length)` in `Gpu_memory.ml`, populated by `free_buffer`/
`free_all_buffers` (`Transfer.ml:378-413`) instead of immediately calling
`B.free ()`, and drained by `ensure_buffer` before it calls
`alloc_scalar_buffer`/`alloc_custom_buffer`. This is the standard
allocator-pool shape (e.g. PyTorch's caching allocator) and slots
cleanly between the existing `Vector.get_buffer` check and the existing
`alloc_*_buffer` calls in `Transfer.ml:187-219` — no change to the
`DEVICE_BUFFER` interface needed, just an intermediate cache lookup.

**Gain**: eliminates driver-level alloc/free overhead for repeat-shaped
scratch buffers in iterative workloads (solvers, training loops); the
magnitude is workload-specific (dominant when iteration count is high and
per-iteration compute is otherwise small) but this is a well-established win
class in every major GPU runtime that added a caching allocator.

**Cost: S-M.** Self-contained to `Gpu_memory.ml` + the two call sites in
`Transfer.ml`.

**Priority: medium** — real but only matters for workloads with
per-iteration vector churn; a one-shot compute kernel sees no benefit.

## 7. Occupancy-aware launch configuration

**Current state**: block/grid dimensions are **always caller-specified**,
everywhere. `Execute.dims1d`/`dims2d`/`dims3d` (`sarek/execute/Execute.ml:
599-606`) are thin wrappers around a literal size the caller passes in;
`grid_for`/`grid_for_size` (lines 608-615) just do the ceiling-division
`(problem_size + block_size - 1) / block_size` — `block_size` itself is
still a caller-chosen constant. A repo-wide check
(`grep dims1d|grid_for sarek/tests/e2e/*.ml`) shows **108 matches** across
the e2e test/benchmark suite, and every one follows the pattern in
`test_nbody_ppx.ml:126,148-149` — `let threads = <hardcoded constant>` then
`dims1d threads`. There is no code path anywhere that queries device
occupancy limits and derives a block size from them.

The device-capability data needed for an occupancy heuristic is **already
queried and stored** at device-creation time and simply unused for launch
config: `Cuda_api.Device.t` (`Cuda_api.ml:105-119`) carries
`max_threads_per_block`, `max_block_dims`, `max_grid_dims`,
`shared_mem_per_block`, `warp_size`, and `multiprocessor_count` —
everything a simplified occupancy calculator needs (CUDA's own
`cuOccupancyMaxPotentialBlockSize` needs register/shared-mem-per-thread
info from the compiled kernel too, which isn't captured anywhere here, so a
*full* occupancy API port needs new kernel-introspection plumbing; a
simplified heuristic — e.g. "round up to warp multiple, cap at
`max_threads_per_block`, default to a `multiprocessor_count`-driven grid
size for underfilled problem sizes" — needs none of that and could ship as
a convenience helper alongside `dims1d`/`grid_for` without touching the
required-explicit path at all).

**Proposal**: add an *opt-in* `Execute.auto_block1d ~device ~problem_size`
helper that reads `device.max_threads_per_block`/`warp_size` and returns a
warp-aligned block size, without removing the explicit `dims1d`/`grid_for`
API — treat as additive convenience, not a policy change, since
kernel-specific register pressure (which this heuristic cannot see) can
make a "bigger block" choice actively worse for register-heavy kernels.

**Cost: S** for the heuristic version (uses data already captured);
**L** for a true `cuOccupancyMaxPotentialBlockSize`-equivalent (needs
per-kernel register/shared-mem usage, which isn't tracked past compilation
today — `Kernel.compile`/`load_module_from_ptx`, `Cuda_api.ml:471-546`,
discard the module's resource-usage attributes after linking).

**Priority: low** — nice-to-have ergonomics, not a bottleneck fix; every
benchmark in the repo already hand-tunes its block size, so there's no
evidence of a live performance problem here, only an ergonomics gap for new
kernel authors.

## 8. Zero-copy / unified memory for integrated GPUs (APU/ZLUDA relevance)

**Current state**: zero-copy already exists as a first-class path — it's not
theoretical. `Transfer.alloc_scalar_buffer_zero_copy`
(`sarek/core/Transfer.ml:93-134`) calls `B.Memory.alloc_zero_copy`, and
`ensure_buffer` (lines 187-219) **tries zero-copy first** for scalar
Bigarray-backed vectors before falling back to a regular `cuMemAlloc` +
transfer. `mark_vectors_stale`'s doc comment (`Execute.ml:362-368`) is
explicit that "Native backend: No-op (uses zero-copy shared memory, no
staleness)" and "OpenCL CPU: Mark stale for custom types (scalar types use
zero-copy)" — i.e. this is a backend-by-backend capability the
zero-copy/unified-memory story already threads through the staleness model
correctly. What's **not clear from this codebase alone** is whether the CUDA
backend's `is_zero_copy`/`alloc_zero_copy` (referenced via the `Framework_sig
.BACKEND` signature, implementation not in `Cuda_api.ml`'s reviewed range —
worth a follow-up check of whichever `Cuda_plugin*.ml` file implements
`Framework_sig.BACKEND.Memory` for CUDA specifically) actually reports
`is_zero_copy = true` on integrated/APU-class devices (relevant to ZLUDA on
AMD APUs, per `project_spoc_zluda` — ZLUDA's CUDA-on-ROCm path on an APU has
genuinely shared system memory, so `cudaHostAllocMapped`-equivalent
zero-copy should be a strict win there, no transfer at all).

**Proposal**: verify (not assume) that the CUDA/ZLUDA backend's zero-copy
detection actually keys off "integrated GPU" device attributes
(`CU_DEVICE_ATTRIBUTE_INTEGRATED` is a real CUDA attribute,
not currently read anywhere in `Cuda_api.ml`'s `get_attribute` calls at
lines 188-215) rather than unconditionally trying and silently falling back
— if it's currently an unconditional-try that just fails and falls back
non-integrated GPUs, that's harmless but wastes one round-trip per vector on
first use; if it's not tried at all for CUDA, that's a missed win
specifically on the ZLUDA/APU target this user cares about.

**Cost: S** to add the `CU_DEVICE_ATTRIBUTE_INTEGRATED` query and confirm/
wire the existing `alloc_zero_copy` path for CUDA; verification-only, no new
mechanism needed since the staleness/dispatch model already supports it.

**Priority: medium**, specifically elevated by the ZLUDA-on-APU angle
(`project_spoc_zluda` memory) — this is the one item where the "gain" is
conditional on a fact (does the CUDA backend's `alloc_zero_copy` actually
fire on APUs today) that needs a direct check before estimating impact
further.
