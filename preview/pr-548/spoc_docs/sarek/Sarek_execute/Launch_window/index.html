Module Sarek_execute.Launch_window

Deferred launch window with horizontal fusion (specs/launch-window.md).

Execute submits JIT launches here instead of issuing them. Pending launches are kept in groups, in submission order. A new launch joins the newest pending group it is compatible with, provided it conflicts with no launch in that group or in any later one. Otherwise it opens a group of its own. A group of several launches is issued as one horizontally fused kernel (Fusion_horizontal); a group of one is the original launch.

Conflicts. Each launch carries the buffers its vector arguments bind and whether the kernel reads or writes each one (Kernel_access). A buffer is named by its vector's id: every device buffer belongs to exactly one vector (only Transfer.ensure_buffer installs one, in that vector's own table), so on one device two arguments share memory exactly when they are the same vector. Device addresses are not used: Vulkan reports none and OpenCL reports object handles. Two launches on the same device conflict when they bind the same buffer and at least one of the two accesses writes. A launch is never moved before a launch it conflicts with, so every conflicting pair is issued in submission order.

Flushing. flush issues every pending group. Execute installs it as the Spoc_core.Launch_hooks flusher, so every synchronisation point flushes before it acts. At most max_groups groups are pending: a new group beyond that issues the oldest one first.

Extension point. A launch is a plain record. A later stage that specialises a launch (for instance a launch-time kernel rewrite) can map launch values before submit without touching grouping or flushing.

This module depends only on the IR and Stdlib, so it builds for jsoo too.

val create : int32_arg:(int32 -> 'arg) -> arg_buf:('arg -> int option) -> arg_int32:('arg -> int32 option) -> set_pending:(int -> unit) -> guard:((unit -> unit) -> unit) -> 'arg t

create ~int32_arg ~set_pending ~guard makes an empty window. int32_arg builds a scalar argument for the fused kernel's position parameters. set_pending is told the number of pending launches after each change. guard f runs f (the issuing of pending groups) with the synchronisation hooks disabled on this domain. Each window has its own slot in the Ir_memo record of every IR it sees; the slot lives as long as that IR, not as long as the window.

Public operations

val flush : 'a t -> unit

Issue every pending launch, in order. The pending count stays non-zero until they are all issued, so a synchronisation point reached meanwhile on another domain waits for this flush (on w.lock) instead of going ahead (FR-007).

val submit : 'arg t -> 'arg launch -> unit

Defer l. When l needs a new group and the window is full, the oldest group is issued first; if that raises, l is not submitted and the exception propagates (the launching call fails before its own launch is accepted, so its vectors' state is unchanged).

val touches : 'a t -> device_id:int -> buf:int -> bool

true when a pending launch on device_id binds vector buf.
