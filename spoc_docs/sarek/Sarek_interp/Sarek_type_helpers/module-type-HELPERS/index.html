Module type Sarek_type_helpers.HELPERS

Module signature for type-specific helpers

type t
val type_id : t Sarek_ir_types.Type_id.t
val from_values : Sarek_value.value array -> t
val to_values : t -> Sarek_value.value array
val get_field : t -> string -> Sarek_value.value
val field_names : string list

Immediate field names, in declaration order — the SAME order to_values produces and from_values consumes, so a name's position in this list IS its index in the value array of the VRecord.

That correspondence is what makes an in-place field STORE possible: get_field can only read, and going through to_values/from_value round-trips via the OCaml record and therefore COPIES, which is how the interpreter came to refuse v.(i).f <- e outright (backlog-172).

For a PPX-generated helper the correspondence holds by construction: the list comes from the same labels list that generates to_values and get_field, so those three cannot drift. For a HAND-WRITTEN implementation it is an obligation the author carries, not a guarantee — the one in-tree hand-written implementor (sarek/sarek/test/test_sarek_type_helpers.ml) maintains it manually, and its own test checks field_index against to_values' output rather than against hardcoded slots so that a drift there fails.

Empty for a variant, which has no named fields.

Breaking for out-of-tree implementors. This is a new REQUIRED val in a public module type, so any HELPERS implementation outside this repository stops compiling until it adds the list. There is no non-breaking spelling: a module type cannot carry a default, and the index cannot be derived from the rest of the signature — to_values needs a value of type t and lookup has none. Adding the obligation is the price of being able to WRITE a field at all; every in-tree implementor is PPX-generated except the test mock above.
