Sequential Execution

Runs all threads in sequence with proper BSP barrier synchronization. Uses the same effect-based approach as parallel, but without domains.

val run_block_sequential_bsp : block:(int * int * int) -> grid:(int * int * int) -> block_idx:(int * int * int) -> (Sarek_cpu_runtime_types.thread_state -> Sarek_cpu_runtime_types.shared_mem -> 'a -> unit) -> 'a -> unit

Run a block sequentially with BSP-style barrier synchronization. Same algorithm as run_block_with_barriers but simpler since no parallelism.

Optimized version: pre-allocate thread states and reuse effect handlers.

val run_sequential : block:(int * int * int) -> grid:(int * int * int) -> (Sarek_cpu_runtime_types.thread_state -> Sarek_cpu_runtime_types.shared_mem -> 'a -> unit) -> 'a -> unit

Parallel Execution

Uses OCaml 5 Domain parallelism with effects for fibers.

  • Fixed pool of N domains (one per core)
  • Blocks are distributed across domains
  • Threads within a block run as fibers with proper barrier sync

BSP Model: For barrier-based kernels, we use a superstep execution model: 1. Each thread is a fiber that can be suspended at barriers 2. All threads run until they hit a barrier (or complete) 3. When all threads have reached the barrier, all are resumed 4. Repeat until all threads complete

The Barrier effect is declared in the sequential section above.

val run_block_with_barriers : block:(int * int * int) -> grid:(int * int * int) -> block_idx:(int * int * int) -> (Sarek_cpu_runtime_types.thread_state -> Sarek_cpu_runtime_types.shared_mem -> 'a -> unit) -> 'a -> unit

Run a block with BSP-style barrier synchronization. Each thread is a separate fiber. All threads run until barrier, then all resume together.

Uses Effect.Shallow for better performance - avoids reinstalling handlers on every resume, which is significant for BSP execution with many barriers.
