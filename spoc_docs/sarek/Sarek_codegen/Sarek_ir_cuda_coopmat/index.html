Module Sarek_codegen.Sarek_ir_cuda_coopmat

Cooperative matrix (SCoopmat) for the CUDA-C generator, which HIP shares.

One generated source serves both toolchains, so every construct here is emitted twice under the platform guard the generator already uses for its f32 barrier: the __HIP_PLATFORM_AMD__ arm is RDNA3 (gfx11) WMMA through the clang builtins, the other arm is nvcuda::wmma. See specs/coopmat-hip-wmma.md for the configurations, the per-lane layout and the reasons for both choices.

What is validated where. The AMD arm is executed on an RX 7900 XTX (gfx1100) against the interpreter: bit-identical for the integer configurations, within the derived bound for f16. The NVIDIA arm is compile-checked only (NVRTC, and ptxas/nvdisasm when present): no NVIDIA GPU was available to run it. The CUDA/C backend does probe coopmat (Cuda_coopmat.support: f16 from sm_70, 8-bit from sm_72, never on ZLUDA), so on an NVIDIA device the launch gate admits what this arm emits. The CUDA/PTX backend does not use this module: it lowers to wmma.* instructions itself (Sarek_ir_ptx_coopmat), for the same configurations.

val buffer_elttype : C.fragment -> Sarek_ir_types.elttype

The kernel buffer element type a fragment may be loaded from or stored to. Integer accumulators of either signedness live in an int32 buffer, and both 8-bit operand types in a uint8 buffer (an s8 fragment also accepts an int8 one, see accepts_buffer): the signedness is the fragment's, applied by the instruction, exactly as the interpreter narrows the loaded byte.

val elttype_name : Sarek_ir_types.elttype -> string
val accepts_buffer : C.fragment -> Sarek_ir_types.elttype -> bool

An s8 fragment also loads from an int8 buffer: the bytes are the same, and it is the natural home of int8-quantised data. uint8 stays accepted.

val check_buffer : buffers:(string * Sarek_ir_types.elttype) list -> buf:string -> C.fragment -> unit

buffers maps a parameter or shared-array name to its element type, when the generator knows it. An unknown name is left to the C++ compiler, which rejects a mismatch too: each helper below takes exactly one pointer type.

val kernel_buffers : Sarek_ir_types.kernel -> (string * Sarek_ir_types.elttype) list

Element types of the kernel's array parameters and shared arrays. A shared array is declared either in kern_locals (DShared) or in the body, as SLet (v, EArrayCreate (elt, _, Shared), _) (how the matrix rewrite declares its staging arrays); private arrays are not buffers.

type operand_layout =
  1. | Loaded of C.layout
  2. | Both_layouts

The layout every CM_load of an operand fragment uses, by fragment name. nvcuda::wmma fixes an operand's layout in its fragment TYPE, so the CUDA arm of the declaration needs it; a name loaded in both layouts has no CUDA spelling. Keyed by name across the whole kernel, scopes ignored: two fragments that share a name in different blocks and are loaded in different layouts get the #error too (conservative, never wrong code).

Launch shape

val check_block : Sarek_ir_types.kernel -> (int * int * int) -> unit

The lowering runs the matrix instruction on whole wavefronts (wave32 on gfx11) and whole warps; a block whose thread count is not a multiple of 32 has a partial wave whose inactive lanes would feed the instruction undefined operands. Refused before any source is compiled.
