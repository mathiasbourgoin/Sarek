Module Sarek_codegen.Sarek_ir_ptx_coopmat

Cooperative matrix (SCoopmat) for the PTX generator: the wmma.* instructions of the PTX ISA (tensor cores from sm_70, PTX ISA 6.0).

The lowering accepts exactly what the nvcuda::wmma arm of Sarek_ir_cuda_coopmat accepts: 16x16x16 on subgroup (warp) scope, any layout of A (row/col), B (row/col) and of the accumulator in memory, and two families of configuration.

  • f16 operands with an f32 accumulator (sm_70);
  • 8-bit operands of the SAME signedness (s8*s8 or u8*u8) with a 32-bit integer accumulator of either signedness (sm_72), wmma.mma ... .s32.s8.s8.s32 or .s32.u8.u8.s32: a 32-bit wrapping sum has the same bits either way. Mixed-sign operands have no wmma form and are refused (a named #error on CUDA/C). The non-saturating form only. bf16 is refused by both: nvcuda::wmma's bf16 fragment reads a bf16 buffer, not a float32 buffer rounded on load.

wmma and not mma.sync: mma.sync.m16n8k16 needs sm_80, and the Turing form m16n8k8 is not translated by ZLUDA (specs/zluda-mma-nvrtc13.md). wmma is the one form sm_70 and later share, and CUDA/C already lowers to it.

Fragments. PTX fixes the per-lane register group of a wmma fragment (m16n16k16): an f16 operand is 8 .b32 registers each holding an f16x2 pair, an 8-bit operand 2 .b32 registers of four bytes, an f32 accumulator 8 .f32 registers and an integer accumulator 8 .b32 registers. The emitter never indexes into a group; it passes the whole group to wmma.load / wmma.mma / wmma.store, which agree on the distribution across lanes.

Precondition, checked at run time. Exactly the CUDA/C one (sarek_cm_require): the element address is 32-byte aligned and stride * element bytes is a multiple of 16, otherwise the kernel executes trap. wmma.load/wmma.store are undefined on a misaligned address; a trap is preferable to wrong results. A .shared array a cooperative-matrix statement accesses is declared 32-byte aligned, so only a misaligned offset into it traps.

What is validated where. Text and refusals: unit tests, any machine. The instructions are checked by ptxas where it is installed. Execution needs an NVIDIA GPU of compute capability 7.0 or later; ZLUDA rejects wmma.*.

Layouts

type operand_layout = Sarek_ir_cuda_coopmat.operand_layout
val operand_layouts : Sarek_ir_types.kernel -> (string * C.layout) list

The layout of every operand fragment of the kernel, by name; refuses a name loaded in both layouts. wmma.mma names the layouts of A and B and expects the fragments to have been loaded in them, so a fragment has exactly one (the CUDA/C arm fixes the same thing in the fragment's type).

val accessed_buffers : Sarek_ir_types.kernel -> string list

The arrays a load or store of the kernel accesses. A .shared one among them is declared 32-byte aligned (Sarek_ir_ptx_types.shared_align), so a tile at index 0 passes the address check whatever its neighbours are.

Kernel-level gate

val sm_number : Stdlib.String.t -> int option

sm_number "sm_86" is 86; a suffix (sm_90a) is ignored.

val check_kernel : ?block:(int * int * int) -> sm_target:Stdlib.String.t -> Sarek_ir_types.kernel -> unit

The whole-kernel refusal, run before any instruction is emitted (a per-node refusal would name whichever node the emitter reached first). A uint8 buffer without a cooperative-matrix statement is ordinary 8-bit storage (Sarek_ir_int8) and is not this function's business. Also the launch shape: the instructions run on whole warps, and a partial warp has inactive lanes that would feed them undefined operands.
