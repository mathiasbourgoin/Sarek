Keep-alive ledger for stream-ordered work

A copy or launch enqueued on a stream may still be reading or writing its operands after the call returns. The backends see raw addresses, which are not GC roots, so SPOC roots the operands here — Bigarray sources and destinations, the vectors involved — until it KNOWS the work has completed:

  • the stream was synchronised (synchronize_stream, destroy_stream), or its device was (flush, Device.synchronize);
  • an event recorded after the work was synchronised, or queried complete;
  • transitively: when a stream b that waited on an event of stream a completes past that wait, a's work up to the event has completed too. This is what releases a copy stream that is never synchronised itself — the spoc_llm M3 pattern (copy on a, record e, b waits on e, sync b).

Entries are ordered by a per-stream sequence number. The ledger is protected by a mutex and is never touched from a GC finaliser (which could run inside Mutex.protect on the same domain and self-deadlock).

type entry = {
  1. seq : int;
  2. keep : keep;
    (*

    Rooted for liveness only; never inspected.

    *)
  3. vec_ids : int list;
  4. host_ranges : (nativeint * int) list;
    (*

    (address, bytes) in flight.

    *)
}
type stream_state = {
  1. sid : int;
  2. sdev : Device.t;
  3. mutable next_seq : int;
  4. mutable pending : entry list;
  5. mutable waits : (int * stream_state * int) list;
    (*

    (seq of the wait on this stream, waited stream, its seq)

    *)
  6. nonblocking : bool;
    (*

    Created with ~non_blocking:true: the default stream does not wait for it, so implicit paths must settle it themselves.

    *)
  7. mutable drain : unit -> unit;
    (*

    Synchronise the stream; set by create_stream.

    *)
  8. mutable destroyed : bool;
    (*

    Set by destroy_stream. A destroyed handle is refused: the driver may have recycled it, and work enqueued through it would land in a ledger nothing consults any more.

    *)
}
