Pending GPU work

Launches are asynchronous: Kernel.execute appends a dispatch to its queue's open command buffer and returns. At each launch the open command buffer is committed if the queue's previous one has completed (the GPU would otherwise idle) or once it holds SPOC_METAL_BATCH dispatches; otherwise it stays open until the next launch, wait, event record or synchronisation commits it. This table remembers every open or committed command buffer that nobody has waited for yet, per command queue, with the MTLBuffers it binds, so that every point where the host can observe or modify device memory waits for exactly the work that touches it:

  • a host read or write of a buffer (whole or ranged copy, read-back) waits for the pending command buffers that bind that buffer (wait_buffers);
  • a launch on one queue first waits for pending work on OTHER queues that binds any of its buffers (wait_buffers_on_other_queues). Within one queue Metal orders command buffers itself: buffers are allocated with the default tracked hazard mode, so a command buffer reading what an earlier one on the same queue wrote waits for it on the GPU;
  • device synchronisation waits for everything (wait_all), stream synchronisation for its queue (wait_queue).

The two waits run before, not atomically with, the copy or launch they guard: two domains that launch on different queues, or copy and launch, on the same buffers at the same moment must order themselves, as on every backend.

Freeing an MTLBuffer needs no wait: a command buffer retains the buffers it binds until it completes, so a release only drops SPOC's reference.

A command buffer that ends in MTLCommandBufferStatusError raises kernel_launch_failed at the first wait that observes it, naming every kernel the command buffer ran: the command buffer, not the dispatch, is the unit of failure, and that wait may be for an unrelated buffer of the same batch. Failures still pending at exit are waited for and reported on stderr (at_exit).
